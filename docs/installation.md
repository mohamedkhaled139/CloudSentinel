# Installation and deployment

CloudSentinel ships as one container image (API, scheduler and web console) plus a database.

* **Try it** – the demo stack with synthetic data and a few real targets: [Demo](#demo-environment).
* **Run it** – Docker Compose with PostgreSQL: [Production with Docker Compose](#production-with-docker-compose).
* **Hack on it** – from source: [development.md](development.md).

Requirements: Docker 24+ with Compose v2, *or* Python 3.11+ and Node.js 20+ for a source install.
CloudSentinel itself needs ~150 MB of RAM for small installations.

## Demo environment

```bash
git clone https://github.com/mohamedkhaled139/CloudSentinel.git
cd CloudSentinel
docker compose -f deploy/demo/docker-compose.yml up --build
```

Open <http://localhost:8000> and sign in with `demo@example.com` / `demo-password-123`.

The demo contains:

* a fictional 13-component platform with dependencies, a week of **synthetic** history, incidents and
  risk findings (all labelled *Synthetic*), generated by `cloudsentinel seed-demo`;
* **real** monitors against an nginx container (HTTP + TCP) and a Prometheus container (PromQL), so you
  can stop a container (`docker compose -f deploy/demo/docker-compose.yml stop web`) and watch a real
  incident open, correlate and auto-resolve.

The demo credentials and secret key are public. Never expose the demo stack to a network.

## Production with Docker Compose

```bash
git clone https://github.com/mohamedkhaled139/CloudSentinel.git
cd CloudSentinel
cp .env.example .env
# Edit .env: set CS_SECRET_KEY and POSTGRES_PASSWORD (generate with the command in the file)
docker compose up -d --build
```

Open <http://localhost:8000>. If you did not set `CS_BOOTSTRAP_ADMIN_*`, the first visit shows a
setup screen that creates the administrator account. Check health with
`curl localhost:8000/readyz`.

### TLS and reverse proxy

Run CloudSentinel behind a TLS-terminating reverse proxy (nginx, Traefik, Caddy, an ingress
controller). The session cookie is marked `Secure` automatically when requests arrive over HTTPS
(set `CS_COOKIE_SECURE=true` to enforce it). Example (Caddy):

```
sentinel.example.com {
    reverse_proxy 127.0.0.1:8000
}
```

When the proxy is not on the same host, start the server with
`cloudsentinel serve --host 0.0.0.0 --forwarded-allow-ips <proxy-ip>` so client IPs (used for login
rate limiting) are taken from `X-Forwarded-For`.

### Upgrades

Database migrations run automatically on startup (`cloudsentinel migrate` runs them explicitly).

```bash
git pull
docker compose up -d --build
```

Back up the database before upgrading between minor versions.

### Backups

All state lives in the database. For PostgreSQL:

```bash
docker compose exec db pg_dump -U cloudsentinel cloudsentinel > cloudsentinel-$(date +%F).sql
```

Keep `CS_SECRET_KEY` with your backups: without it, stored integration credentials cannot be
decrypted (they can be re-entered).

## Kubernetes

Example manifests are in [`deploy/kubernetes/`](../deploy/kubernetes): read-only RBAC for the
Kubernetes integration and a single-replica Deployment using an external PostgreSQL. Run a single
replica (it hosts the scheduler), or run extra API replicas with `CS_SCHEDULER_ENABLED=false` and a
separate `cloudsentinel scheduler` Deployment with one replica.

## Source install (without Docker)

```bash
cd frontend && npm ci && npm run build && cd ..
cd backend && python -m venv .venv && . .venv/bin/activate
pip install ".[postgres]"
export CS_ENVIRONMENT=production CS_SECRET_KEY=... CS_DATABASE_URL=postgresql://...
export CS_STATIC_DIR=$PWD/../frontend/dist
cloudsentinel serve --host 0.0.0.0 --port 8000
```

A systemd unit for this setup:

```ini
[Unit]
Description=CloudSentinel
After=network-online.target postgresql.service

[Service]
User=cloudsentinel
WorkingDirectory=/opt/cloudsentinel
EnvironmentFile=/etc/cloudsentinel.env
ExecStart=/opt/cloudsentinel/backend/.venv/bin/cloudsentinel serve --host 127.0.0.1 --port 8000
Restart=always

[Install]
WantedBy=multi-user.target
```

## SQLite vs PostgreSQL

SQLite (the default) is fine for evaluation and small single-node installations. Use PostgreSQL for
production: it handles concurrent writes from the scheduler and API better and supports standard
backup tooling. Both are covered by the automated test suite.
